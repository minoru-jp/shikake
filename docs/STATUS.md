# shikake development status

shikake `0.0.3` is prepared for publication on October 24, 2026; actual PyPI and GitHub publication is a separate manual workflow. Versions `0.0.1` and `0.0.2` were released previously. This status describes implemented functionality, limitations, and test evidence. See the [Changelog](../CHANGELOG.md) for release-specific changes.


## v0.0.3: implicit built-in bindings and generalized collections

- Version 0.0.3 treats built-in names as virtually introduced at the beginning of each parsed module, with `BindingState.introduction="builtin"`. Module-level writes, deletes, and possible star-import conflicts update the usual rebinding/deletion flags, without changing lexical-local bindings.
- Query a parsed module Model using `PackageModel.bindings_for(module, name)`, or the matching module Model using `SourceInspection.bindings_for(module, name)` for complete single-source inspection. The queried implicit name need not occur in `name_bindings`, which continues to enumerate source-written binding facts. These methods match scope Model identity and do not perform runtime name resolution. Distinct annotation and function/class lexical scopes may share one definition Model; the returned `NameBinding.scope_kind` distinguishes them. User-created NameBinding values may omit the optional field (`None`).
- The standard built-in set is fixed by Python minor version, excluding `site` conveniences (`help`, `exit`, etc.) and runtime mutations; Python 3.15 includes `frozendict`, `sentinel`, `ImportCycleError`, and `__lazy_import__`. A test compares the fixed inventory to a clean CPython interpreter launched with `-S -I`. Dynamic modifications to built-ins and target-version substitution are not modeled. Collection Kinds and Structures have breaking changes; Features remain unchanged.
- Collections are normalized to `model.value.collection.sequence`, `.mapping`, or `.set`, all using `collection_construction` with `construction`, `immutable`, and `inputs`. Direct literal inputs retain their written elements/entries; recognized built-in calls retain argument Models; comprehensions retain their original clause-bearing Model under `inputs`. A generator expression remains outside Collection. List/tuple binding targets are represented separately as `model.structural_part.sequence_target`. Calls are normalized only when the built-in name is not shadowed or written in its visible lexical scopes and the constructor argument syntax is supported (0–1 positional arguments; no `*`; keywords only for `dict`/`frozendict`). PEP 695 type parameters are visible from generic bodies, method scopes, annotations, bases, and type-alias expressions, but not from decorators or function defaults. Annotation scopes directly beneath a class (including annotation-only nesting) can see class locals, while ordinary method and nested class bodies cannot. Package-level resolved star imports can report a more precise three-axis binding than single-file conservative Collection normalization. A comprehension Collection wraps its preexisting comprehension Model, allowing identical spans during `walk()`. This is deliberately conservative, not runtime type inference. Source code which uses the former concrete Collection Kinds and roles must migrate.

## Implemented functionality

- The distribution and public import name are `shikake`. Internal code resides in `shikake._mica`; no top-level `mica` package is distributed. The runtime Shikumi dependency is `>=0.2.4,<2.0.0`.
- Source strings and local Python source trees, including directories without `__init__.py`, are read using the AST to produce Kinds, Structures, Features, and role-based Models. By default all regular `.py` files in a designated tree are considered; `extensions` selects other or additional suffixes, while `include(path, is_directory)` prunes subdirectories and filters matching files. No directories are excluded by default; child symlinks are not followed. Module-name conflicts are checked after selection, and Partial completeness applies to selected inputs. All selected files are parsed as Python AST regardless of suffix. The `filename` argument of `parse_source()` can identify syntax errors.
- All four analysis APIs default to `syntax_validation="compile"` for AST parsing plus non-executing CPython compilation checks, and accept `"ast"` to skip the compilation check for restricted dialects. Compilation does not guarantee runtime validity. Python 3.15 PEP 798 unpacking comprehensions are modeled, including a distinct dictionary-unpacking child Model and Structure; explicit lazy imports use the usual import Kinds and Structures with the `lazy` Feature on the statement. Runtime import timing is not modeled.
- Strict APIs: `parse_source()` and `parse_package()`. Partial APIs with diagnostics: `inspect_source()` and `inspect_package()`. All four accept an optional `import_policy`: `unrestricted` (default), `registered_interfaces` (explicit registered interface imports only), or `registered_modules` (registered external modules plus caller-specified absolute `allowed_modules` names). Restricted modes reject relative and star imports, but allow the single `from __future__ import annotations` directive. Explicit registered-interface imports are valid in both restricted modes. Import targets are never resolved or executed, and this is not a security sandbox.
- Models expose `parts()`, `get(role)`, `get_scalar()`, and `walk()`; `format_model_tree()` provides a bounded diagnostic tree display. The `analyses` option selects inheritance and override candidate analyses. Known single- and multiple-inheritance graphs can yield same-name method candidates without ranking them, and each written base expression has a `BaseReference`. A shared AST fact index collects declarations and binding events per scope, including nested classes.
- Trusted Shikumi definitions or an `ExternalDefinitions` object built with `ExternalDefinitionsBuilder`, supplied through `definitions=`, can register custom Kinds and Structures for explicitly imported external interface calls. Registered external structures and their child attributes cannot be used as values outside permitted direct-call forms; indexing or similar operations on a **call result** retain ordinary Models. `shikake.external` exposes both the Shikumi declaration API and a programmatic builder. No dynamic resolution or execution is performed.
- Internally, Python 3.13-and-earlier baseline modeling rules are refined by Python 3.14 and 3.15 rules, without user-selectable model-version modes or version labels in Models. The parser models Python 3.12 `type` statements and generic declarations, Python 3.13 type-parameter defaults, and Python 3.14 t-strings (`TemplateStr` / `Interpolation`). Python 3.14 unparenthesized multiple-exception handlers reuse the existing exception-handling Model. Interpreter-specific test results are recorded in the verification section below. CI targets Python 3.11–3.15. The built-in catalog has 143 Kinds, 62 Structures, and 2 Features. See the [LAYOUTS specification source](../devdocs/canonical_sources/specification/layouts.py) for the catalog.

## v0.0.2: source comments

- The explicit `collect_comments(source)` API extracts raw `#` comments using `tokenize`, returning an immutable `SourceComments` result with `Comment` items. It supports source-order access, inclusive line ranges, trailing comments, upward searches blocked only by code lines (not blank lines), and module header/footer queries.
- These are **independent lexical facts**, not Model children, Features, inferred type annotations, or ownership relationships. Type comments remain uninterpreted, and all current AST parsing retains `type_comments=False`.
- CR, LF, and CRLF use AST-compatible line numbers. `SourceComments` must be constructed through `collect_comments()`; direct construction or `dataclasses.replace()` is unsupported, while copy/pickle round-trips work. For file-based sources use `tokenize.open()` to decode encoding cookies and BOMs, and pass the same string to comment collection and Model parsing. Only sources parseable by the current Python AST have guaranteed comment results; invalid sources can yield differing errors or comments across Python versions. Tokenizer character columns differ from UTF-8 byte columns in AST `SourceSpan`. Tokenization errors apply only to the explicit comment API and do not change strict/partial AST parsing. No separate Model-origin query is planned: pass an available `Model.span.line` or `.end_line` to the line-query APIs. A `span=None` Model has no line to supply. Models sharing a line receive the same line-query results; comment ownership and the common origin of the source are not verified. Package-wide comment queries are not provided; call `collect_comments` for each source. To query comments immediately above a function or class body, pass the first body statement's `span.line` to `above_line()` only if the same line has no preceding code; for decorated definitions query the earliest decorator start line to find comments above the definition. For trailing comments on an assignment's last line, pass the assignment statement's `span.end_line` to `on_right_of_line()`. `in_lines()` covers multiline constructs. None of these infer comment ownership. Comment collection uses Python's standard-library `tokenize` and adds no runtime dependencies.

## Base references and three binding dimensions

- `PackageModel.base_references` and `bases_for(class_model)` provide a `BaseReference(subject, expression, targets, binding, attribute_modified)` for each written base expression. `targets` are discovered class candidates; `binding` is the root name's `BindingState(introduction, may_rebind, may_delete)` or `None`; `attribute_modified` indicates explicit attribute modification within the same module. When the root name is a standard built-in name with no same-named binding in an inner visible scope, `binding` is the module-level built-in state (for example, `class AppError(Exception)` with no same-named write gives `BindingState("builtin", False, False)`).
- `PackageModel.name_bindings` and `bindings_for(scope, name)` expose name-binding facts per lexical scope, even when `analyses=set()`. Complete single-source `inspect_source()` results also expose `SourceInspection.name_bindings`; incomplete Partial results expose no binding facts. These are not Features; explicit `lazy` does not change their evaluation rules or static reference candidates. They distinguish initial syntactic introduction, subsequent or repeatable writes, and deletions without deciding execution order, branch outcomes, or definite assignment at a read.
- There is no global certainty status for an inheritance graph. Base-reference facts and override candidates are reported separately; consumers decide what to do with candidates. The AST fact collector is shared with external-structure validation.

## Internal performance behavior

- Each Model instance lazily caches its structural hash. Hashing a parent Model also caches the hashes calculated for its descendants, avoiding repeated traversal when those descendants are queried later. Structural equality, hash computation rules, and iterative traversal are unchanged.
- `PackageModel.bindings_for()`, `bases_for()`, and `overrides_for()` use internal indexes built when the PackageModel is created. Keys rely on Model object identity, not structural hashes; result contents, order, and the empty-tuple behavior are preserved.
- These optimizations introduce no public API. They incur some Model initialization and first-hash caching costs, and PackageModel indexing requires additional construction time and memory.
- `repr(package)` provides a bounded diagnostic summary of the composition Model, selected analyses, and relationship counts without expanding the relationship facts. Full information remains available through attributes and lookup methods.
- `repr(source_inspection)` displays the Model summary and name-binding count without expanding each binding. Both inspection result types retain full `issues` in their representations, so a large collection of diagnostics can still produce a long string.

## Release automation

- Ordinary pushes and pull requests run checks through `.github/workflows/ci.yml`; they do **not** publish to PyPI. Start `.github/workflows/release.yml` manually using **Actions → Release to PyPI → Run workflow** on the default branch.
- The release workflow checks Python 3.11–3.15 and the extracted sdist, builds and verifies the distributions, then publishes to PyPI using Trusted Publishing with the `pypi` GitHub Environment. **Only after successful PyPI publication** does it create a `v<project.version>` Git tag (for v0.0.3, `v0.0.3`) on the published commit and a GitHub Release with the built distributions.
- A new release run refuses to republish an already tagged version. If tagging or GitHub Release creation fails after publication, select **Re-run failed jobs** on the *same workflow run*, not **Re-run all jobs**, to avoid uploading the same version to PyPI again. If the PyPI upload outcome is uncertain, check PyPI before retrying.
- Configure a matching PyPI Trusted Publisher for this GitHub repository, workflow file `release.yml`, and GitHub Environment `pypi` (a pending publisher may be used for the first publication). This describes the configured workflow, **not** proof that an actual release has completed.

## Known limitations and issues

- `shikake.Model` is a public **result type**, intended to be read from supported parsing APIs. Direct `Model(...)` construction is unsupported; validity of user-created Models and the behavior of other APIs receiving them are not guaranteed. Kind/Structure/Feature consistency guarantees apply to Models produced through the library's normal parsing paths.
- Strict analysis rejects unsupported syntax with `UnsupportedSyntaxError`. Partial analysis can report available results, but `complete=False` means the result is incomplete. Local external-call errors may omit a statement while retaining later Models, so the omission may also affect how those later Models can be interpreted. On an incomplete package, Partial analysis does not produce base references, override candidates, or name-binding relations.
- The standard Python AST parser imposes depth limits. Several Model construction, traversal, equality, hashing, binding, and method-search paths are iterative, but arbitrarily deep or unbounded analysis is not promised. Partial analysis does not convert `RecursionError` into a diagnostic.
- No automatic discovery of external packages or `.pyi` files is provided. Registered external-call matching requires explicit top-level imports and does not support directly imported free functions. It rejects ambiguous rebinding or unsupported argument forms. Instance-level type inference is not performed. Static base-class candidates are not runtime identity proofs and may not cover runtime-dependent targets. Multiple written bases and candidates can be represented, but runtime MRO, precedence, and generic-base resolution are not computed. The absence of a static candidate does not prove its runtime absence.
- Source code is never executed. Value evaluation, type inference, dynamic name resolution, and code translation are out of scope.
